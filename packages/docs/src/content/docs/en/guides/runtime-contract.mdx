---
title: Runtime Contract
description: Use one request runtime context across Node, AWS Lambda, and Cloudflare Workers.
---

Croco exposes adapter runtime details through `Context.getRuntimeContext()` from
`@croco/framework-context`. Application code can read one request-scoped contract without depending on
Node, API Gateway, or Workers-specific objects.

Runtime context describes the active host request; it does not combine runtime composition into one
concept. A **Host** owns the environment lifecycle, a **Transport** executes a protocol surface, and
a **Build Target** describes the deployable artifact. Generated manifests record those axes
independently.

The contract is provided by Croco-owned host paths such as `createLambdaHost()` and
`createCloudflareWorkersHost()`. `createApp().fetch()` is the HTTP transport callback those hosts
invoke. `lambdaHandler()`, `listen()`, `toWorkersHandler()`, and `createWorkerFetchHandler()` remain
compatibility surfaces that also establish their documented runtime context. Explicit raw Hono
forwarding is another compatibility path and does not provide the Croco runtime contract.

```typescript typecheck
import { Context } from "@croco/framework-context";
import { Controller, Get } from "@croco/protocols-rest";

@Controller("/runtime")
class RuntimeController {
  @Get("/context")
  context() {
    const runtime = Context.getRuntimeContext();

    runtime?.waitUntil(Promise.resolve());

    return {
      platform: runtime?.platform,
      requestId: runtime?.requestId,
      canUseEnv: runtime?.capabilities.env,
      canUseWaitUntil: runtime?.capabilities.waitUntil,
    };
  }
}
```

## Capability Matrix

| Capability         | Node HTTP                        | AWS Lambda                                                           | Cloudflare Workers                          |
| ------------------ | -------------------------------- | -------------------------------------------------------------------- | ------------------------------------------- |
| `platform`         | `node`                           | `lambda`                                                             | `cloudflare-workers`                        |
| `env`              | supported through `process.env`  | supported through `process.env`                                      | supported through the Worker binding object |
| `filesystem`       | supported                        | supported for the Lambda filesystem, including `/tmp`                | unsupported                                 |
| `nodeApi`          | supported                        | supported on the Node.js Lambda runtime                              | unsupported                                 |
| `requestLifecycle` | supported per HTTP request       | supported per invocation                                             | supported per fetch event                   |
| `requestId`        | `x-request-id` or generated id   | API Gateway request id or `awsRequestId`                             | `x-request-id` or generated id              |
| `logger`           | app logger                       | app logger                                                           | app logger                                  |
| `trace`            | active HTTP server span          | active HTTP server span                                              | `traceparent` when present                  |
| `waitUntil`        | unsupported                      | queued and drained before response conversion                        | delegates to `ExecutionContext.waitUntil`   |
| `flush`            | unsupported                      | drains queued work and can run transport-provided telemetry flushing | unsupported                                 |
| `shutdown`         | unsupported in the request scope | unsupported in the request scope                                     | unsupported in the request scope            |

The code-level source of truth for these runtime and capability names is
`RUNTIME_CAPABILITY_SUPPORT` from `@croco/framework-context`. `RuntimeContextInit<"cloudflare-workers">`
cannot declare `flush: true` or provide a `flush` hook, while `RuntimeContextInit<"lambda">` can declare
`flush: true` only with a concrete flush implementation.
Custom adapter platforms can still use a custom `platform` string, but they must pass an explicit
capability support config when creating a runtime context so unsupported hooks are rejected instead of
falling back silently.

## Runtime Composition Metadata

`RuntimeCapabilityManifest.composition` records host, transports, and build target separately. The
host uses one `platform` and lifecycle, each transport records a protocol and optional package, and
the build target records artifact metadata without claiming lifecycle ownership.
Each manifest describes one selected runtime composition. A project that ships optional host
entrypoints keeps the default composition in the canonical manifest and documents the alternative
entrypoints explicitly; the manifest is not an inventory of every deployable variant.

```typescript typecheck
import { createRuntimeCapabilityManifest } from "@croco/framework-context";

const manifest = createRuntimeCapabilityManifest("lambda", {
  composition: {
    host: {
      platform: "lambda",
      lifecycle: "invocation",
      packageName: "@croco/preset-lambda",
    },
    transports: [
      {
        protocol: "http",
        packageName: "@croco/transports-http",
      },
    ],
    buildTarget: {
      name: "lambda-function",
      format: "cjs",
      outputDirectory: "dist",
    },
  },
});
```

This metadata does not create the host or transport. Build tools and policy checks consume it to
detect drift without inferring composition from a preset name.

## Binding Host Callbacks

Create application objects inside an `ApplicationRuntime` scope and wrap retained host callbacks
with `bindHostCallback()`:

```typescript no-check
import { createApplicationRuntime } from "@croco/framework-module";
import { createLambdaHost } from "@croco/preset-lambda";
import { createApp } from "@croco/transports-http";

const runtime = createApplicationRuntime();
await runtime.initialize();

const app = runtime.run(() => createApp({ controllers: [] }));
const lambdaHost = createLambdaHost(app);

export const handler = runtime.bindHostCallback(lambdaHost);
```

Every invocation re-enters the owning application scope. After `runtime.dispose()`, the bound
callback rejects access through the runtime's disposed-state failure instead of running with stale
providers.

## Declaring Requirements

Package authors should declare runtime needs as `RuntimeCapabilityRequirement` values and validate
them against the generated runtime manifest instead of branching on platform names in application
code.

```typescript typecheck
import {
  checkRuntimeCapabilityRequirements,
  createRuntimeCapabilityManifest,
  type RuntimeCapabilityRequirement,
} from "@croco/framework-context";

const requirements = [
  { capability: "waitUntil", source: { file: "src/jobs/register.ts" } },
  { capability: "nodeApi", source: { file: "src/reports/export.ts" } },
] satisfies RuntimeCapabilityRequirement[];

const manifest = createRuntimeCapabilityManifest("cloudflare-workers");
const diagnostics = checkRuntimeCapabilityRequirements(manifest, requirements);

if (diagnostics.length > 0) {
  throw new Error(diagnostics.map((diagnostic) => diagnostic.code).join(", "));
}
```

Use `source.file`, `source.line`, and `source.column` when a requirement comes from generated
metadata or package manifests. Unsupported requirements fail with stable
`CROCO_RUNTIME_CAPABILITY_001` diagnostics, so package checks, generated app smoke, and release
evidence can point authors back to the exact declaration that must move to another runtime or remove
the unsupported capability.

## Native Context

Use `runtime.native` only at adapter boundaries:

- Lambda stores `{ event, lambdaContext }`.
- Cloudflare Workers stores `{ executionContext }`.

Prefer capability checks before reading runtime-specific objects. Missing features are represented as
`capabilities.<name> === false` and no-op hooks, not as hidden platform assumptions.
Adapter authors must not advertise unsupported capabilities as available. Croco rejects erased JavaScript
inputs that claim a platform/capability combination the matrix does not support or claim a hook-backed
capability without a hook implementation.

## Lambda Telemetry Flush

`runtime.flush()` drains Croco runtime work queued through `runtime.waitUntil()`. OpenTelemetry export stays
owned by `@croco/telemetry-sdk-node`, so Lambda apps should connect `TelemetryRuntime.forceFlush()` at the
Lambda host boundary:

```typescript no-check
import {
  TelemetryForceFlushUnsupportedProblem,
  TelemetryRuntime,
  lambdaPreset,
} from "@croco/telemetry-sdk-node";
import { createLambdaHost } from "@croco/preset-lambda";

const telemetry = TelemetryRuntime.getInstance();
await telemetry.init(lambdaPreset({ serviceName: "orders" }));

const lambdaHost = createLambdaHost(app, {
  flush: async () => {
    const result = await telemetry.forceFlush(5000);
    if (result.outcome === "failed") {
      throw result.error;
    }
    if (result.outcome === "unsupported") {
      throw new TelemetryForceFlushUnsupportedProblem();
    }
  },
});

export const handler = runtime.bindHostCallback(lambdaHost);
```

The callback runs after the request and queued runtime work complete. If it rejects, the Lambda handler rejects
instead of returning a business success without export evidence. A disabled runtime reports `skipped`, while only
a processor that performed the flush reports `completed`.
